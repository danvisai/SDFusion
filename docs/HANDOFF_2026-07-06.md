## What shipped this session (chronological)

1. **Layer 2.5a: procedural weathering** (`de14e76`) — `scene/sdf_weather.py::weather_grid`
   ages a building by displacing its final detailed SDF grid before marching cubes: convex-edge
   wear via the SDF Laplacian, fBm surface erosion boosted near the ground, Worley-ridge crack
   carving in noise-gated patches. Pure procedure, no data, deterministic per (seed, intensity).
   Wired into `town_export.build_building_mesh` via `b["weather"]`/`b["weather_seed"]`; index.html
   got a Weathering slider. Sheets: `outputs/weathering/weather_{probe,building}.png`.

2. **Layer 2.5b v0: heritage-scan ornament retrieval** (`df0fc64`) — user wanted real
   architectural ornament (reliefs/friezes), not synthesized. `scripts/foundations/
   ingest_ornaments.py` downloads + normalizes real heritage-scan meshes (threedscans.com open,
   3 reliefs seeded: Romanesque ox panel, Angkor Wat + Bayon casts; a Smithsonian Open Access
   CC0 backend exists via `--smithsonian` but is API-key rate-limited) into `data/ornaments_v1/`
   (gitignored, reproducible). `scripts/server/ornaments.py` did retrieval (style→culture
   affinity) + fit (scale/yaw/sink onto a wall). v0 placement was a hand-coded "longest wall,
   fixed height" heuristic.

3. **Layer 2.5b upgrade: learned ornament placement** (`b81df48`) — user explicitly rejected
   the external-API angle and the hand-coded heuristic: "don't depend on external APIs, let's
   train or use a model to attach things." Chose (via AskUserQuestion) to keep the local mesh
   library but replace placement with already-trained models, zero new training:
   `layout_detail.propose_ornament_slot` asks `PartLayoutPlannerV2` (same model that places
   balconies/columns elsewhere) for a flush wall slot — BuildingNet has no ornament/relief
   label, so a sampled `balcony`/`balcony_upper` instance stands in as the closest analogue.
   Retries up to 4 draws (single-draw hit rate is only ~10%) and weights candidates toward the
   wall band vs. the roof taper (measured: pitched roofs are only ~57% full-width before
   narrowing). `layout_detail.place_ornament` then deconflicts the slot against existing detail
   ops via `CoherentPartRefiner` (`integrate_new_part`, the same model coherent-add uses). Caught
   and fixed a real bug mid-session: re-deriving the placed panel's facing normal by re-querying
   its own already-boundary-snapped position is numerically degenerate (near-zero vector before
   normalization) — fixed by keeping the first-draw normal instead. Hit rate 80–93% across
   classes. Sheets: `outputs/weathering/ornament_learned_{placement,facing}.png`.

4. **Frontend coherence audit** (`9853a61`, `1d15e3b`, `8f83a85`) — user asked to audit
   index.html (town page) vs sculpt.html (SDF Sculptor) for duplicated/incoherent features and
   fix them. Summary:
   - **Confirmed but NOT a bug**: two separate trained models both decide facade detail
     (`PartComposer`, always-on statistical facade; `PartLayoutPlannerV2`, explicit draggable
     parts) — already coherent, both pages share `PartComposer` identically. The asymmetry
     (index.html can't directly invoke the planner for an explicit layout the way sculpt.html's
     "✨ AI details" can) is an accepted, scoped gap — see the scope decision below.
   - **Scope decision (AskUserQuestion, both recommended options chosen)**: keep the two pages
     intentionally distinct (town page = fast browsing: ornaments/weathering/whole-town export;
     Sculptor = precision editor: AI-details planner/manual placement/gizmo) rather than full
     feature parity, but make the round-trip between them lossless. Also removed
     Snap-to-plausible from index.html to match sculpt.html's 2026-07-03 doctrine (procedural/
     learned-model placement only, never diffusion remolding); `/refine_with_edit` stays
     server-side for API/test use (`test_branches.py` B9 exercises it directly).
   - **Bug 1 (fixed)**: index.html's `adapt()` (restyle/height/class/🎲variation) replaced the
     mesh with a bare regenerated one, silently discarding any tower/ornament/weathering already
     applied. Fixed: route through `rebuild()` instead of `setMesh()`.
   - **Bug 2 (fixed)**: opening a building in the Sculptor started from a completely different
     random massing (`sample_params(seed=None)` is non-deterministic, and the `seed` URL param
     was built by index.html but never actually read by sculpt.html). Any Sculptor work then
     overwrote the town mesh on "Apply to town" while the town's own edits list stayed stale.
     Fixed with a real round-trip: `/building_sdf` gained an optional `recipe_params` override
     (exact reproduction, bypasses re-sampling); index.html stashes `{bid, params, edits}` via
     `localStorage['sculptResume']` before opening the tab; sculpt.html converts edits
     world↔cube via new `worldToCubeOp`/`cubeToWorldOp` JS helpers; `applyTown()` sends the edit
     list back (not just the mesh) via `localStorage['townApply']`; index.html's storage handler
     sets `b.edits` and calls `rebuild()` so weathering/ornaments correctly re-apply.
   - **Bonus bug (fixed)**: `compose_detail`'s `apply_roof_shape` is an unconditional union with
     no awareness of existing geometry — a Sculptor-placed manual roof replacement would get
     doubled once round-tripped (and was already double-applying inside sculpt.html's own bake,
     independent of the round trip). Fixed via `composer_detail.auto_roof_flag(edits)` + a new
     `roof=` param on `compose_detail`, wired at all 3 call sites. **Deliberately did NOT** add
     the same guard for `door=`: `det:'door'` is also set by the wing/balcony Make-it-architecture
     constructions' own door sub-op and by AI-details' exactly-one-door regularization —
     suppressing the composer's door there would remove the building's only entrance. If a
     Sculptor door-replacement feature is ever added, this needs a distinct tag (e.g.
     `door_manual`), not reuse of `det:'door'`.
   - **Bug 3 (fixed, found live by the user after Bug 2 shipped)**: the round-trip fix loaded
     resumed edits into sculpt.html without the `layer` tag (`'mass'` vs `'detail'`) that
     `interpretSel()` uses to decide what's re-interpretable, and defaulted the selection to the
     *last* loaded op. A typical tower construction's ops end with a run of window carves
     (shaft+cap built first, windows last), so resuming a tower selected a tiny untagged window
     box instead of the tower body — "🧠 Make it architecture" looked broken/inert. Fixed:
     tag `layer:(det?'detail':'mass')` on resumed ops, select the first mass-layer op by default.
   - **Bug 4 (fixed, found live by the user immediately after Bug 3 shipped)**: fixing Bug 3
     made the resumed tower's body correctly selectable — which exposed that `interpretSel()`'s
     non-reroll cleanup only ever removed the single selected op (`edits.splice(sel,1)`), fine
     when that branch could only be reached for a fresh ungrouped `addPrim()` primitive. Once an
     already-constructed body (sharing a `grp` with its own cap/windows) became selectable,
     clicking "Make it architecture" left those siblings orphaned while building a new
     construction on top — a doubled, overlapping mess. Fixed: group-aware removal
     (`edits.filter(e=>e.grp!==srcOp.grp)` when the op has a `grp`), matching what re-roll
     already did.
