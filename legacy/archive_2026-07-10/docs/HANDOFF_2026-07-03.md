## In-progress: index.html wiring (RESUME HERE)

**Goal**: give `index.html` the same Make-it-architecture mechanism sculpt.html has, replacing
its sole reliance on the diffusion prior for tower/dome/wing additions.

**Why it's not a copy-paste of the sculpt.html wiring**: `index.html`'s buildings are stored in
a completely different frame than sculpt.html's. sculpt.html operates on a single cube-frame
`[-1,1]³` SDF volume; `index.html`'s building object (`b = {footprint, position, style, cls,
height, seed, params, edits, styleRef}`, see `index.html:152`) is **world-meter frame** —
footprint in local building meters, `edits` built by `buildEdit()` (`index.html:229-232`) with
centers/sizes in meters relative to the footprint. `/interpret_mass` expects cube-frame
(`base_sdf_b64` + op in `[-1,1]` coords). A conversion bridge is needed.

**Plan worked out but not yet implemented**:
1. Add a new endpoint (e.g. `/interpret_mass_world`) in `inference_service.py` that:
   - Takes `{footprint, style, building_class, height, recipe_params, seed, op (world
     meters), existing_ops (world meters, optional)}`.
   - Calls `refiner().building_volume(footprint, style, recipe_params, height, res=64)` →
     gets back `(grid, center, scale, height_norm)` — **note `building_volume` takes
     `recipe_params` directly**, so pass `b.params` as-is; no need to re-sample via seed.
   - Converts `op`'s world center/size into cube-frame: `cube_center = (world_center -
     center)/scale`, `cube_size = world_size/scale` (same pattern already used earlier this
     session in the coherent-add-bake test's `world_box_op()` helper — check
     `scripts/server/test_coherent_add_bake.py` or similar for the exact reference
     implementation if it still exists).
   - Calls `layout_detail.interpret_mass(grid, cube_op, building_class, style, seed,
     temperature)`, and if `existing_ops` given, also converts those and calls
     `integrate_new_part` (reuse, don't duplicate).
   - Converts the result `ops` back to world-meter frame (inverse transform) and returns
     `{kind, source, coherent, ops (world-frame), n}`.
2. On the frontend, replace the `snap(buildEdit(selected, kind))` call pattern
   (`index.html:239`) for the tower/dome/wing quick-add buttons with a new
   `makeArchitecture(buildEdit(selected, kind))` that POSTs to the new endpoint, pushes the
   returned world-frame `ops` into `b.edits` (replacing the crude placeholder), then needs a
   **procedural-only** mesh regeneration call — **this last piece was still being investigated
   when the handoff was requested**. Was checking whether `/params_to_mesh` or
   `/regenerate_building` already support applying `edits` procedurally (CSG + composer detail,
   no diffusion) the way `/export_town`'s internal per-building path does
   (`recipe_base_sdf(...) → EditableBuilding(edits).composed() → detail_cube_volume`). From
   what was read (`inference_service.py:102-180`), **neither currently accepts an `edits`
   param** — `ParamsToMeshReq` and `BuildingReq` both lack it. Likely need either:
   (a) a small new endpoint that does the same procedural compose+detail+mesh path
   `/export_town` already does per-building, exposed for a single building, or
   (b) extend `/regenerate_building` to optionally take `edits` and apply them procedurally
   before detailing.
3. Keep the existing `/refine_with_edit` sdedit path around (don't delete — unlike sculpt.html,
   no explicit instruction yet to remove Snap from `index.html` entirely, only to add the
   procedural alternative alongside/instead for the quick-add buttons specifically). Confirm
   with the user whether they also want the `✨ Snap to plausible (AI)` button removed here too,
   or kept as a manual option.
4. Re-run both gates after, plus a targeted live test analogous to the sphere/cone one (POST a
   tower/dome/wing add through the new endpoint against a real town building, check the
   returned ops are sane world-frame values, not blown up).
